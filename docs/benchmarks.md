## Interpretation

Everything above is generated; this section is written by hand and is kept when the report is
regenerated. It cites numbers from this report, from the first run of the same suite where the
variance table makes that useful, and one diagnostic probe (marked as such) that measured the
connection behaviour the micro-benchmarks imply.

### The single-use connection is the dominant cost of a small query

The design opens a fresh MySQL connection per query (`SetMaxIdleConns(0)`, no pooling, so the
read-only session variables are always re-applied). That is visible in the micro-benchmarks and in
the load numbers:

| Measurement | Direct query | Through `RunReadOnly` | Overhead |
|---|---|---|---|
| `SELECT 1`, ns/op | 14,385 | 351,969 | +337 µs (24x) |
| `SELECT 1`, allocs/op | 14 | 174 | +160 |
| 1000 rows, ns/op | 254,804 | 941,764 | +687 µs (3.7x) |
| 1000 rows, allocs/op | 6,019 | 12,193 | +6,174 |

A direct probe (not part of the scripted suite: `Connections` read before and after a 30 s S2 cell)
counted 26,621 new MySQL connections for about 24,600 calls — **1.08 new connections per query**.
That connect/handshake is roughly a third of the ~1 ms p50 gap between S1 (no database, p50 0.3 ms
at c=1) and S2 `SELECT 1` (p50 1.3 ms); the rest is the query round trip and the result handling.

For large results the connection stops mattering and materialisation dominates: S4 (1000-row cross
join) is 66.5 rps at c=1 and 231 rps at c=32, with p50 rising from 14.8 ms to 137 ms while still
reporting zero errors.

### Concurrency: short query cells fail from connection churn, not from query cost

Every failure in this run was the same sanitized tool error, `database unavailable` — the request
reached the handler and the handler could not open its MySQL connection:

| Cell | Failures |
|---|---|
| S2 `SELECT 1` @ c=8 | 38.1% (8,706 of 22,821) |
| S2 `SELECT 1` @ c=32 | 15.4% (4,126 of 26,729) |
| S3 `SELECT * FROM orders` @ c=1 | 11.6% (1,464 of 12,581) |
| S3 @ c=8 / @ c=32 | 7.7% / 21.7% |
| S1, S4, S5, S6 (all concurrency levels) | 0 |

The rate is not stable between runs: in the first run of this same suite S2 @ c=8 failed 48.0%
(9,807 of 20,441); the mechanism and the cells that fail are the same, the level is not. Read these
as "a large fraction of calls fails in these cells", not as exact percentages.

Two observations bound the cause. First, MySQL's own limits were never reached: `max_connections 40`,
`Max_used_connections 13`, `Connection_errors_max_connections 0`, `Aborted_connects 6` after the
whole suite, so the server was not refusing logins. Second, the failures land in the cells that push
the connection rate highest, not in the cells whose statements cost most: S1 and S6 open no
connection and never fail; S4 and S5 run the slowest statements but open far fewer connections per
second and never fail; the failures are all in S2 and S3, the cheap statements hammered in a loop.
Within that group the level is not monotonic in concurrency (S2 gets better from c=8 to c=32, S3
gets worse 11.6% → 7.7% → 21.7%), which fits a host-level accept limit rather than the server's own
queue [INFERENCE: at c=32 the excess concurrency is rejected before it opens a connection, while
c=8 sits exactly at `MAX_CONCURRENT_QUERIES`, so more of its calls reach the connect path].

Two changes that would explain a refusal upstream were tried and rejected by diagnostic probes on the
same stack: raising `back_log` and `thread_cache_size`, and pointing the DSN at the container's IP so
the name no longer has to resolve. Neither moved the failure rate, so DNS resolution and MySQL's
backlog setting are both ruled out. (Those probes were short single-cell runs and this rate is not
stable between runs, so their absolute values are not comparable with the table above; what they show
is that neither change altered the outcome.) The measured shape points at host-side accept/thread
churn: c=1 runs 654-704 calls/s, about 1.08 connections each, so ~710-760 new connections/s with zero
failures, while c=8 completes 760 calls/s and fails 38% — about 1,050 connection attempts per second
on this shared 4 vCPU host.

### What to do with this

- Keep client concurrency at or below 4 for short queries on hardware like this; c=1 ran 654-704 rps
  with zero failures, while c=8 loses between a third and a half of its calls.
- Raising `MAX_CONCURRENT_QUERIES` does not address these failures: every failure was a connection
  that could not be opened, not a call rejected by the queue. The two changes that would move the
  limit are a connection pool (which gives up the fresh-session guarantee the single-use design
  buys) or running MySQL on a separate host.
- The guard is negligible at realistic sizes: `GuardCheck` is 870 ns for a short statement, 31.8 µs
  for 1 KiB and 2.19 ms at the 64 KiB `MaxSQLBytes` ceiling. It does allocate about 75-100x the
  statement size (6.6 MB, 21,948 allocs at the ceiling), so a tighter SQL length limit is the lever
  if a guard-heavy deployment ever shows memory pressure.
- Timeouts work: `QUERY_TIMEOUT=2s` against `SELECT SLEEP(30)` returned at 2.01 s and the statement
  was gone from the processlist at 2.12 s.
- Treat absolute throughput as indicative. The server and MySQL share one 4 vCPU host, so the
  numbers exclude network latency entirely, and run-to-run variance reached 22% (S2 @ c=8 p50).
